# Decisions log

Format: `YYYY-MM-DD, phase NN: decision, reason`

- 2026-09-24, phase 00: Stack is Three.js + Colyseus + TS monorepo. Browser-first for fast solo iteration and link-shareable playtests.
- 2026-09-24, phase 00: Multiplayer from day one. Solo testing via multiple tabs, headless bots and simulated latency.
- 2026-09-24, phase 00: No client prediction in the MVP. Action-based sync (from/to + start/end tick) with interpolation instead. Grid actions last 150–500 ms, so input delay at typical ping should be acceptable. Revisit after the latency test.
- 2026-09-24, phase 00: Falls ignore other players in the MVP. Death keeps keys.
- 2026-09-24, phase 00: PvP is push/knock-off (ARCHITECTURE §14), planned after the MVP. In Key Race with PvP, a death drops 1 key back to its spot. Second mode: Knockout arena.
- 2026-09-24, phase 01: Colyseus 0.18 (server `colyseus@0.18.8`, `@colyseus/schema@5.0.34`, client `@colyseus/sdk@0.18.4`; the old `colyseus.js` package is replaced by `@colyseus/sdk`). Server uses `defineServer`/`defineRoom`; schema uses the `schema({...})` + `t.*` helper, so no decorators are needed.
- 2026-09-24, phase 01: No build step for server/shared/bots. They run from TS source via `tsx`, and shared is linked as TS source (`exports: ./src/index.ts`). `npm run build` = typecheck + Vite client build. Add emitted JS only if deployment needs it.
- 2026-09-24, phase 01: TypeScript 7 (native `tsc`) with `moduleResolution: bundler` and `.ts` import extensions everywhere.
- 2026-09-24, phase 01: `.env` is loaded with Node's built-in `process.loadEnvFile` (no dotenv dependency).
- 2026-09-24, phase 02: `Dir` and `Action` are `as const` objects plus union types, not TS `enum`s. Same values, and they stay erasable (Node type stripping, isolatedModules).
- 2026-09-24, phase 02: Pulses use one buffer slot. Within one input message jump beats turn; across messages the latest wins. That is how "jump > turn" works with a single slot.
- 2026-09-24, phase 02: A pulse is valid while `tick - pulseTick <= INPUT_BUFFER_TICKS`, where `pulseTick` is the world tick when the input arrived (so it's usable on the next 6 steps). A pulse is spent when tried, even if blocked. A blocked pulse falls through to held fwd on the same tick.
- 2026-09-24, phase 02: Reservations are derived each tick from player state and not stored. Flip and Jump also reserve their pass-through cell (A / A1). A falling player reserves its current and next cell, so others can't move in, but its own fall ignores reservations (§5). Dead players reserve nothing.
- 2026-09-24, phase 02: With no free spawn (on respawn or on join), the player stays Dead and retries every tick. `addPlayer` uses the same path.
- 2026-09-24, phase 02: Key pickup and the exit win are resolved when the action finishes (§7 step 2), in the same rotated player order as starts. Only the timeout is checked in step 4. After a result, keys and exit are frozen but movement keeps running; the server decides when to stop stepping.
- 2026-09-24, phase 02: The time limit counts from world creation (tick 0), so the server should create the world when `playing` starts.
- 2026-09-24, phase 02: The level check for "no duplicate item cells" also covers spawns (spawn/key/exit must all be distinct).
- 2026-09-24, phase 02: Added dev dependency `@vitest/coverage-v8` (required by the phase's coverage check).
- 2026-09-24, phase 03: `GameState.tick` is a round clock. It runs from -60 to 0 during the countdown, equals `world.tick` while playing (so action start/end ticks share its timeline), and keeps counting through results. `phaseEndTick` is on the same clock, so the client can show any phase's remaining time as `(phaseEndTick - tick) / 20`.
- 2026-09-24, phase 03: The room uses Colyseus `setFixedTimestep(step, 20)` (fixed-step accumulator with capped catch-up) for the 50 ms simulation. Patch rate stays at the default 50 ms.
- 2026-09-24, phase 03: Room settings (level, MIN_PLAYERS) come only from the server config module, never from client join options, so clients can't pick the level or bypass the player minimum. Tests override the exported `config` object.
- 2026-09-24, phase 03: `LATENCY_MS` is passed to Colyseus `server.simulateLatency()`, which treats it as round-trip ms. It's ignored when NODE_ENV=production. `.env` is still loaded with `process.loadEnvFile`, and real env vars take precedence.
- 2026-09-24, phase 03: Leaving during countdown/playing removes the player from the world. If no players remain in the world, the room returns to the lobby. A player who leaves during the lobby can make the remaining players "all ready", which starts the countdown.
- 2026-09-24, phase 03: The integration test uses an in-process `defineServer` on port 2598 plus `@colyseus/sdk`, not `@colyseus/testing`, so there's no extra dependency.
- 2026-09-24, phase 04: The client keeps a render-side history of each player's last 3 action segments and renders the one running at `renderTick`. The schema only carries the current action, and rendering 2 ticks behind would otherwise snap forward whenever a chained roll replaces from/to. Idle segments start at their `endTick`, because the sim keeps the finished action's ticks.
- 2026-09-24, phase 04: `poseAt` returns the frame orientation (X = left, Y = up, Z = fwd) plus a per-action rolling `spin`. The client accumulates spin across segments as render-only state, so the stateless pose function doesn't snap the ball's rotation at each tile.
- 2026-09-24, phase 04: The follow camera is `frameQuat × Q0`, where Q0 is a constant local look-down orientation. Its position is `ball + frame·(0, 2.5, −4)`. There is no world-space `lookAt`, so a 90° change of up can't gimbal-flip it. Both are damped with `1 − exp(−10·dt)`.
- 2026-09-24, phase 04: The key light is attached to the camera, since there is no fixed sky when gravity can point along any axis.
- 2026-09-24, phase 04: Dev helpers: F8 freezes the rendered frame (for screenshots), F9 downloads a canvas PNG, and `window.kula` (DEV builds only) exposes net/players for automation.
- 2026-09-24, phase 04b: Jump like the original. `Action.Hop = 7` is appended, and `Cmd` gains `'hop'`. When a jump pulse is used, `commands()` produces `['jump', 'hop']` if fwd is held on that tick, otherwise `['hop']`. So a blocked forward jump falls back to a hop, and the pulse is spent once. A hop reserves only its own cell and is blocked by a block at C+U.
- 2026-09-24, phase 04b: Latency experiment, local ball at `estServerTick − 1` (others stay at −2). Measured input→motion, 6 single-tile taps each:
  - LATENCY_MS=0: 196 → 139 ms.
  - LATENCY_MS=150: 354 → 290 ms.
  - Late-segment snaps: 0 in all four runs, each including 8 s of chained rolls/flips.
  - **Kept −1.** It can be overridden with `?localInterp=2`. The F3 "late segs" counter watches for snaps on real networks with jitter; `simulateLatency` has none.
- 2026-09-24, phase 04b: `RenderPose.lift` (the jump/hop height) is added, and the follow camera tracks `position − up·lift`. If the camera follows the hop height, the ground moves instead of the ball, and a hop barely reads.
- 2026-09-24, phase 04b: The client calls `room.leave()` on `pagehide`. Navigating to a new URL put the old page in the back/forward cache, where it kept its seat, so the next join became a spectator.
- 2026-09-25, phase 04c: Held jump + forward latch (ARCHITECTURE §5/§6).
  - `Input.jumpHeld` is required: `parseInput` rejects messages without it.
  - `setInput` sets `fwdLatch` on a fwdHeld false→true edge while the player is Hopping.
  - `commands()` priority: jump pulse or latch → `jumpCmds(fwdHeld || latch)`; buffered turn; `jumpHeld` → `jumpCmds(fwdHeld)`; `fwdHeld` → roll. The latch is cleared at every decision.
  - The client sends the jump pulse with the Space keydown, so a tap shorter than one tick still bounces once.
  - A turn tapped early in a hop can expire before landing (INPUT_BUFFER_TICKS = 6 of the hop's 10), as with any pulse.
- 2026-09-25, phase 04c: Blob shadow per ball.
  - It's projected along the dominant axis of the rendered `up` onto the first block within 3 cells, sits 0.01 above the face, and fades with height.
  - Mid-flip the dominant axis points into air over the edge, so during a Flip the shadow keeps its last placement instead of blinking off.
- 2026-09-24, phase 04b: Ball contact (`−U·0.1` along the pose's `up`) was already in place from phase 04. It was verified visually on a side face.
- 2026-09-25, phase 05: Pulse buffer. `pulseTick` is replaced by `pulseAge`, which advances each tick the player is not airborne (Hop, Jump, Fall). A turn or jump pressed at any time during a jump or hop now applies on landing. While grounded, or dead waiting to respawn, pulses still expire after INPUT_BUFFER_TICKS. The old expiry test used a Jump to keep the player busy, so it now uses a Dead wait instead.
- 2026-09-25, phase 05: `findPath` (shared `sim/path.ts`) is a BFS over (cell, up, fwd) with moves fwd/left/right/jump through `previewAction`, ignoring players. `resultPose` follows a forward jump's fall to its landing and drops moves that end out of bounds. `outOfBounds` moved to `sim/world.ts` so the tick and the pathfinder share it.
- 2026-09-25, phase 05: Seek bots press one step at a time and release fwd/jump once the server shows the action started. They may press in the last tick of a Roll/Turn/Flip. They wait while another player is on A1/A2 before a forward jump, because a short jump can drop them into a gap.
- 2026-09-25, phase 05: `LEVEL` accepts a comma list; the room rotates it at each countdown (`state.levelId` changes). The client keys item meshes by id + cell, because the exit keeps its id across levels.
- 2026-09-25, phase 05: Death feedback is shown where the ball was last rendered (the client notices its rendered action turning Dead), not at the event's cell, which sits KILL_MARGIN below the level and is usually off screen.
- 2026-09-25, phase 05b: Instant mid-air turning.
  - In `step`'s input-apply pass, an airborne player (Hop/Jump/Fall) with a buffered turn pulse turns at once: `to.fwd = turnFwd(to.up, to.fwd, dir)`, the pulse is consumed, and `turnFromFwd`/`turnStartTick` are recorded.
  - `to.cell`, `to.up`, `endTick` and reservations are untouched. Grounded turns stay TURN_TICKS actions; turns during Roll/Flip still buffer.
  - `startAction` resets the record only when it's older than TURN_TICKS. A turn on the landing tick of a chained hop otherwise snapped at 150 ms latency, because the next hop started on the same tick and cleared it.
- 2026-09-25, phase 05b: `PlayerS` gains `turnFromFwd` (uint8) and `turnStartTick` (int32).
  - The client updates an in-flight segment in place when only its `to`/turn record changes (same action and ticks), so air turns don't count as late segments.
  - `poseAt` takes an optional `AirTurn` and slerps the facing over TURN_TICKS for Hop/Jump/Fall; position still follows `from`.
- 2026-09-25, phase 05b: Spawn shuffle. `createWorld` stores `spawnOrder`, a Fisher-Yates shuffle of the spawn indices using `mulberry32(seed)`, and `trySpawn` uses the first free spawn in that order. The server seeds each round with its round number. The test helper `inOrder(world)` pins level order for tests that place players by spawn.
- 2026-09-25, phase 06: Push resolution (ARCHITECTURE §14), all inside `resolveMoves`.
  - A player's intent is its first command that would start, checked against the start-of-tick reservations. It's a push only when that command is `fwd` and a non-Dead player on the same face stands in `A = C + F`. A forward jump into a player still falls back to a hop, as in the MVP.
  - Stages, each in fair order: 1. targeted victims whose intent is a move other than a Turn start it (escape); 2. mutual pushes both bounce; 3. other pushes; 4. everything else. Non-push moves resolve after pushes, so a knock claims `A + F` before someone rolls into it.
  - A victim whose own intent is a push isn't escaping. In a chain P→V→W, fair order decides: if V goes first, P is blocked (V is rolling); if P goes first, P bounces off V (W is behind V).
  - A push fails with a bounce when `A + F` is solid or reserved by anyone. A pusher still holding W after its stun tries again and bounces again.
  - `isPushable(v, tick)` for a Hop: ticks 1–2 after its start tick and the last 2 before its end, so 4 of every 10 ticks. The start tick itself is the escape tick.
  - Knocking keeps the victim's facing: the Turn's start facing, or a Hop's mid-air turn.
- 2026-09-25, phase 06: Knocked and Stunned. Buffered pulses don't age during either one (the prompt only named Stunned), because a 4-tick knock would otherwise use up most of the 6-tick buffer. A knock that ends on ground runs `onLand`, so being knocked onto a key collects it, and onto the unlocked exit wins.
- 2026-09-25, phase 06: Key drop. `PlayerState.keyIds` records collected keys in order, and a death drops the most recent one. No drop happens after the round has a result (keys are frozen). A dropped key reappears even if a ball is standing on it; that ball collects it the next time it lands there. `lastKnockedBy` is cleared on every death, so a knock can't be credited across a respawn.
- 2026-09-25, phase 06: Rules flag. `createWorld(level, seed, rules = { push: true })`. Tests: `test/util.ts` exports a mutable `rules` that test worlds copy, and `pushOff.test.ts` sets `push = false` and re-imports the pre-push suites (sim, keyRace, heldJump, airTurn, path). This changed 4 lines of test plumbing. One MVP test ("can't roll into a hopping player's cell") pins push off, since with push a low hop is pushable.
- 2026-09-25, phase 06: Push rendering.
  - `poseAt` Knocked: the ball holds for `knockHold` (default 1 of the 4 ticks, while the pusher closes the 0.2-cell gap), then slides along from→to with a quarter-turn spin (`KNOCK_SPIN`).
  - The client adjusts the hold by the local render lead (local ball at −1, others at −2): +1 tick when the victim is local, −1 when the pusher is local. The pusher is found as the view with a Roll that starts on the knock's tick into the victim's cell. At LATENCY_MS=150 this changed the pusher↔victim distance when the knock starts moving from 0.58 to 0.774–0.79 (balls touch at 0.8).
  - Wobble, the flashing ring and the bounce lunge apply to the ball mesh only, not to `RenderPose`, so the follow camera doesn't shake.
- 2026-09-25, phase 06: Bots.
  - Seek takes an off-path push when the opponent ahead would be knocked into air. It also shoves a pushable player standing on a jump's A1 instead of waiting.
  - A step that ends Stunned (a bounce) counts as blocked, like a move that never started, so repeated bounces lead to a replan and then a random turn.
  - `bully` BFS-es to standable cells beside opponents (not into the opponent's own cell, which led to jumping into gaps and stand-offs with seek bots). Next to an opponent, it turns to face it and pushes when `pushable`. If it can't push for 1 s, it ignores that opponent for 3 s.
